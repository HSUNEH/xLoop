# 오픈소스 프로젝트 성장 전략 — 완전 가이드

> 이 문서는 opportunity-scout AI 에이전트가 오픈소스 프로젝트 전략 수립 시 참조하는 핵심 레퍼런스다.
> 프로젝트 설계부터 런칭, 커뮤니티 빌딩, 수익화, 최신 트렌드까지 실전 데이터 기반으로 정리되어 있다.
> 마지막 업데이트: 2026-03-27

## 1. 프로젝트 설계 전략

### 1.1 문제 정의 프레임워크

#### "10x Better" 원칙
단순히 "조금 나은" 도구는 전환 비용을 이기지 못한다. 기존 대안 대비 **최소 10배** 나은 축이 하나는 있어야 채택이 일어난다.

| 10x 축 | 설명 | 성공 사례 |
|---------|------|-----------|
| **속도** | 기존 도구 대비 10-100배 빠름 | Vite(webpack 대비 100배 HMR), Bun(Node 대비 3-4배), esbuild(webpack 대비 100배) |
| **비용** | 무료 또는 1/10 가격 | Supabase(Firebase 대비 무료 셀프호스팅), n8n(Zapier 대비 무료) |
| **단순함** | 설정/코드량 1/10 | FastAPI(Flask 대비 코드량 절반 + 자동 문서화), Hono(Express 대비 미니멀) |
| **접근성** | 사용 장벽 제거 | Ollama(로컬 LLM을 1줄로 실행), LiteLLM(100+ LLM을 단일 API로) |

#### 차별화 포인트 발견법
1. **고통 지도 그리기:** 타겟 영역의 개발자들이 가장 많이 불평하는 것 3가지를 Reddit, HN, GitHub Issues에서 수집
2. **기존 도구 ERRC 분석:**
   - **E(Eliminate):** 필요 없는 기능 제거 → 단순화
   - **R(Reduce):** 과도한 부분 축소 → 경량화
   - **R(Raise):** 부족한 부분 강화 → 핵심 가치
   - **C(Create):** 아예 없는 것 새로 만들기 → 혁신
3. **"Why Now?" 테스트:** 6개월 전에는 불가능했지만 지금은 가능한 이유가 있는가?
   - 새 API 출시 (예: OpenAI Assistants API → 에이전트 프레임워크 기회)
   - 새 표준 채택 (예: MCP 프로토콜 → MCP 도구 생태계)
   - 기술 성숙 (예: WebGPU 안정화 → 브라우저 AI 추론)

### 1.2 아키텍처 결정의 마케팅 영향

아키텍처는 기술적 결정인 동시에 **커뮤니티 성장 전략**이다.

| 아키텍처 | 커뮤니티 영향 | 대표 사례 |
|----------|--------------|-----------|
| **모놀리스** | 기여 장벽 높음, 코드 이해 어려움. 초기 개발 속도 빠르나 커뮤니티 기여 제한적 | 초기 단계 CLI 도구 |
| **모듈러/플러그인** | 핵심 코어는 작고, 플러그인으로 확장. 기여자가 코어를 건드리지 않고 기여 가능 → 기여 장벽 대폭 하락 | Vite(플러그인), ESLint(규칙), Astro(인테그레이션) |
| **마이크로 패키지** | 각 패키지 독립 사용 가능. 선택적 채택으로 도입 장벽 낮음 | Lodash, Radix UI, shadcn/ui |
| **프레임워크 + 어댑터** | 코어 프레임워크 + 플랫폼별 어댑터. 생태계 확장성 극대화 | SvelteKit(어댑터), tRPC(어댑터) |

**플러그인 시스템의 힘:**
- ESLint: 2,800+ 커뮤니티 규칙 → 사실상 모든 JS 프로젝트의 표준
- Vite: 900+ 플러그인 → 프론트엔드 빌드 도구 1위
- Obsidian: 1,800+ 커뮤니티 플러그인 → 노트 앱 시장 장악
- 핵심: 플러그인 시스템 = **"나도 기여할 수 있다"**는 심리적 문 열기

### 1.3 API/DX(Developer Experience) 설계

DX가 좋은 프로젝트는 채택률이 높고 이탈률이 낮다. 개발자는 문서를 읽기 전에 코드를 먼저 시도한다.

#### DX 최적화 원칙

| 원칙 | 설명 | 좋은 예 | 나쁜 예 |
|------|------|---------|---------|
| **제로 설정(Zero Config)** | 설치 즉시 동작 | `npx create-next-app` | 10줄 설정 파일 필수 |
| **점진적 공개(Progressive Disclosure)** | 기본은 단순, 필요할 때 심화 | FastAPI의 자동 기본값 | 모든 옵션을 첫 화면에 |
| **에러 메시지 = 문서** | 에러가 해결 방법을 알려줌 | Elm의 컴파일러 에러 | "Segmentation fault" |
| **복사-붙여넣기 실행** | 예제 코드가 그대로 동작 | 모든 코드 블록 테스트 완료 | import 빠진 코드 예제 |
| **일관된 패턴** | 한 번 배우면 전체 API 예측 가능 | Stripe API의 일관성 | 메서드마다 다른 패턴 |

#### "설치 → 첫 성공" 시간 최소화: 5분 룰

| 단계 | 목표 시간 | 체크리스트 |
|------|-----------|-----------|
| 발견 → 이해 | 30초 | README 첫 3줄로 프로젝트 가치 파악 |
| 이해 → 설치 | 1분 | 1줄 설치 명령어 (`npm i`, `pip install`, `brew install`, `docker run`) |
| 설치 → 첫 실행 | 2분 | 기본 설정 없이 즉시 실행. hello-world 수준 결과 확인 |
| 첫 실행 → "아하!" | 2분 | 핵심 가치를 직접 체험. "이거 진짜 되네!" 순간 |
| **총합** | **5분 이내** | 이 시간을 넘기면 이탈률 급증 |

**원클릭 데모 전략:**
- **GitHub Codespaces / Gitpod:** 브라우저에서 바로 코드 실행 환경 제공
- **StackBlitz WebContainer:** 웹 기반 Node.js 환경으로 즉시 체험
- **Codesandbox:** 라이브 데모 + 코드 편집 동시 제공
- **Docker 원클릭:** `docker run -p 8080:8080 project-name` 한 줄로 전체 체험
- 이러한 원클릭 데모 제공 프로젝트는 미제공 프로젝트 대비 스타 전환율 2-3배 높음

## 2. README + 문서화 전략

### 2.1 README 심리학

GitHub 방문자의 행동 패턴을 이해해야 효과적인 README를 쓸 수 있다.

#### 방문자의 15초 판단 과정
```
0-3초:  프로젝트명 + 한 줄 설명 스캔 → "이게 뭐지?" 판단
3-5초:  배지 확인 → "활발한 프로젝트인가?" 판단
5-10초: 데모 GIF/스크린샷 확인 → "내가 원하는 것인가?" 판단
10-15초: 빠른 시작 섹션 확인 → "쉽게 시작할 수 있나?" 판단
15초+:  스타 클릭 또는 이탈
```

#### 스크롤 패턴
- **F패턴:** 방문자는 첫 줄을 수평으로 읽고, 아래로 내려가며 왼쪽 정렬된 키워드만 스캔
- **상위 20%에 핵심 정보 집중:** README 전체 내용의 핵심은 첫 스크롤(약 600px) 안에
- **시각적 앵커 포인트:** 배지, GIF, 코드 블록이 시선을 잡는 앵커 역할

### 2.2 README Hook-Problem-Solution-Demo 공식

#### Hook (첫 줄 — 3초 승부)
```markdown
# 프로젝트명

한 줄 설명: 무엇을, 누구를 위해, 어떤 결과를

예시:
"Git 커밋 메시지를 AI가 자동 생성합니다. 10초면 완벽한 커밋 메시지."
"SQL 없이 자연어로 데이터베이스를 쿼리하세요."
```

**Hook 공식:** `[동작 동사] + [구체적 대상] + [놀라운 결과/방법]`

- "A comprehensive framework for..." (X) — 추상적, 무의미
- "10초 만에 API 문서를 자동 생성합니다" (O) — 구체적, 수치 포함

#### Problem (왜 필요한가)
- 3-5개 불릿 포인트로 구체적 고통을 나열
- 타겟 사용자가 "맞아, 이거 짜증나" 라고 고개 끄덕이게
- 추상적 "개선"이 아닌, 경험적 고통 묘사

#### Solution (어떻게 해결하는가)
- Problem과 1:1 대응되는 해결 방법 제시
- 기능 나열이 아닌 **결과** 중심으로 서술
- 가능하면 수치 포함 ("3초 만에", "코드 50% 감소")

#### Demo (보여줘라)
- GIF 데모가 텍스트 설명보다 10배 효과적
- "빠른 시작" 섹션: 복사-붙여넣기 가능한 설치 명령어 1-3줄

### 2.3 배지(Badges) 전략

배지는 프로젝트의 "신뢰 시그널"이다. 올바른 배지는 방문자에게 "이 프로젝트는 진지하다"는 인상을 준다.

| 배지 유형 | 효과 | 우선순위 | 예시 |
|-----------|------|----------|------|
| **CI 상태** (passing) | 코드 품질 신뢰 | 필수 | ![build](https://img.shields.io/github/actions/workflow/status/...) |
| **테스트 커버리지** | 코드 안정성 입증 | 높음 | ![coverage](https://img.shields.io/codecov/c/github/...) |
| **npm/pypi 다운로드 수** | 실사용 증거 (사회적 증명) | 높음 | ![downloads](https://img.shields.io/npm/dm/...) |
| **버전** | 활발한 개발 증거 | 중간 | ![version](https://img.shields.io/npm/v/...) |
| **라이선스** | 사용 가능 여부 즉시 확인 | 필수 | ![license](https://img.shields.io/github/license/...) |

**주의:** 배지 5-7개가 적정. 10개 이상은 오히려 산만하고 신뢰 하락

### 2.4 데모/GIF 제작 가이드

첫 인상의 80%는 시각적 요소가 결정한다. README에 데모 GIF가 있으면 스타 전환율이 약 2-3배 높아진다.

#### GIF 제작 도구
| 도구 | 플랫폼 | 특징 |
|------|--------|------|
| **asciinema** | 터미널 | 터미널 녹화, 텍스트 복사 가능, SVG 지원 |
| **VHS (Charm)** | 터미널 | 코드로 터미널 데모 정의, 재현 가능, CI에서 자동 생성 |
| **Kap** | macOS | 가볍고 빠른 화면 녹화, GIF/MP4 |
| **ScreenToGif** | Windows | 화면 녹화 + GIF 편집 |
| **LICEcap** | macOS/Win | 초경량 GIF 녹화 |

#### 효과적인 데모 GIF 규칙
- **15초 이내:** 긴 GIF는 로딩 느리고 집중력 분산
- **핵심 가치 1가지만:** 모든 기능 보여주려 하지 말 것
- **루프 가능하게:** 시작과 끝이 자연스럽게 연결
- **파일 크기 5MB 이하:** 큰 GIF는 README 로딩 지연
- **텍스트 가독성:** 터미널 폰트 크기 키우기 (최소 16px)
- **대안: 짧은 MP4 영상** — GitHub README에 `<video>` 태그 가능, GIF보다 90% 가벼움

## 3. 프로젝트 네이밍과 브랜딩

### 3.1 좋은 프로젝트 이름의 조건

| 조건 | 설명 | 좋은 예 | 나쁜 예 |
|------|------|---------|---------|
| **기억하기 쉬움** | 2-3음절, 발음 가능 | Vite, Bun, Deno | AbstractSyntaxTreeManipulationFramework |
| **기능 암시** | 이름만으로 기능 추측 | FastAPI, LiteLLM | Zephyr (뭔지 모름) |
| **검색 가능** | 구글링 시 다른 것과 안 겹침 | Astro, Turborepo | Go (너무 일반적) |
| **도메인 확보** | .dev, .io, .com 가능 | supabase.com | 이미 점유된 도메인 |
| **npm/pypi 가용** | 패키지명 선점 가능 | 등록 전 확인 필수 | 이미 점유된 패키지명 |

### 3.2 네이밍 전략 패턴

1. **기능 직관형:** FastAPI, LiteLLM, AutoGPT — 검색 발견성 높음
2. **은유/비유형:** Docker(항구 노동자), Kubernetes(조타수), Kafka(작가) — 브랜딩 강함
3. **조합형:** Supabase(Super+Database), Turborepo(Turbo+Repository) — 균형
4. **약자형:** Next.js, Nuxt, Svelte — 짧고 세련됨

### 3.3 브랜딩 요소
- **로고:** 심플한 아이콘 + 프로젝트명. 32x32px에서도 식별 가능해야
- **색상:** 1-2개 브랜드 색상. GitHub, 문서, 웹사이트에서 일관되게
- **태그라인:** 10단어 이내의 설명문. README 첫 줄에 사용
- **프로젝트 웹사이트:** GitHub Pages로도 충분. 있으면 신뢰도 2배 상승

### 4.2 Hacker News (Show HN) 공략법

#### 특성
- 기술적 깊이를 중시하는 커뮤니티. 마케팅 톤 = 즉시 다운보트
- 1위 등극 시 하루에 스타 500-3,000개 가능
- 포스트 수명: 약 12-24시간

#### 제목 작성법
```
공식: "Show HN: [프로젝트명] – [구체적 기능/가치 한 줄]"

좋은 예:
  "Show HN: LiteLLM – Call 100+ LLMs using the same Input/Output format"
  "Show HN: Hatchet – Open-source task queue with built-in observability"
  "Show HN: Unkey – Open source API key management"

나쁜 예:
  "Show HN: We built something amazing that will change how you code"
  "Show HN: Revolutionary AI-powered developer productivity tool"
  "Show HN: Check out our new project!" (아무 정보 없음)
```

#### 최적 게시 시간 (2025 데이터 기반)
| 시간대 | 효과 | 근거 |
|--------|------|------|
| **화-목, 오전 8-10 AM PT** (한국 새벽 1-3시) | 가장 안전한 선택 | 전통적으로 트래픽 최대, 경쟁 적당 |

| **주말** | 예상 외 효과 | 157K+ Show HN 포스트 분석 결과, 경쟁 적어 상위 노출 확률 높음 |

#### Founder Comment 전략
포스팅 후 **5분 이내**에 상세 댓글 작성. 이것이 없으면 참여도가 크게 떨어진다.

**필수 포함 내용:**
1. **개인적 동기:** "이 문제를 직접 겪어서 만들었습니다"
2. **기술적 결정:** "X 대신 Y를 선택한 이유는..."
3. **솔직한 한계:** "아직 Z는 지원하지 않습니다"
4. **피드백 요청:** "어떤 기능이 가장 필요하신가요?"
5. **로드맵:** 향후 1-3개월 계획

#### HN 실패 패턴
- 마케팅 톤 ("revolutionary", "game-changing", "disrupting")
- 기술적 질문에 모호한 답변 또는 미응답
- 초기 2시간 내 댓글 미응답 (순위 결정 시간대)
- 봇처럼 보이는 초기 upvote 패턴 → 페널티 가능

## 5. 커뮤니티 빌딩 심화

### 5.1 기여자 유치 파이프라인

기여자는 저절로 오지 않는다. 체계적인 파이프라인이 필요하다.

#### 파이프라인 단계
```
발견 → 관심 → 첫 기여 → 반복 기여 → 핵심 기여자 → 메인테이너

각 단계 전환율 (현실적 수치):
  발견 (README 방문): 100%
  관심 (스타 클릭):   5-15%
  첫 기여 시도:       0.1-0.5%
  첫 기여 완료:       0.05-0.2%
  반복 기여 (3회+):   0.01-0.05%
  핵심 기여자:        0.005-0.01%
```

#### "Good First Issue" 전략
- **수량:** 항상 5-10개의 good first issue를 유지
- **난이도:** 코드베이스 이해 없이 30분-2시간 내 해결 가능한 수준
- **구체성:** 이슈 본문에 수정 대상 파일, 예상 접근법, 테스트 방법까지 명시
- **다양성:** 문서 수정, 테스트 추가, 간단한 버그 픽스, 번역 등 다양한 유형
- **라벨링:** `good first issue` + `help wanted` + 난이도 라벨 (`easy`, `medium`)

**good first issue 템플릿:**
```markdown
## 설명
[무엇을 해야 하는지 1-2줄]

## 배경
[왜 이것이 필요한지]

## 구현 가이드
- 수정 대상 파일: `src/utils/parser.ts`
- 예상 접근법: [구체적 힌트]
- 참고 코드: [유사한 기존 구현 링크]

## 테스트 방법
- `npm test -- --filter=parser`

## 질문이 있으시면
이슈 댓글로 편하게 질문해주세요!
```

#### CONTRIBUTING.md 필수 항목
1. 개발 환경 설정 (복사-붙여넣기로 실행 가능)
2. 코드 스타일 가이드 (ESLint/Prettier 설정 참조)
3. PR 제출 프로세스 (브랜치 네이밍, 커밋 컨벤션)
4. 리뷰 기대치 (평균 응답 시간, 리뷰어 지정 방법)
5. 커뮤니케이션 채널 (Discord, Discussion 등)

### 6.1 "Awesome List" 등록 전략

Awesome 리스트는 GitHub에서 가장 큰 큐레이션 채널이다. 주요 리스트는 수만~수십만 스타를 보유하며, 등재 시 지속적인 트래픽 유입원이 된다.

#### 등록 방법
1. **관련 Awesome 리스트 탐색:** `awesome-[기술키워드]`로 GitHub 검색
2. **기여 가이드 확인:** 각 리스트의 CONTRIBUTING.md에 등재 기준 명시
3. **기준 충족 확인:** 대부분의 리스트가 요구하는 최소 기준:
   - README가 영어로 작성됨
   - 활발한 유지보수 (최근 6개월 내 커밋)
   - 최소 스타 수 (리스트마다 다름, 보통 50-500개)
   - 명확한 라이선스
4. **PR 제출:** 리스트 형식에 맞춰 한 줄 설명과 함께 PR
5. **리뷰 대응:** 메인테이너 피드백 빠르게 반영

### 6.2 GitHub Trending 알고리즘

GitHub은 정확한 알고리즘을 공개하지 않지만, 커뮤니티 분석으로 핵심 요인이 파악되어 있다.

#### 핵심 요인 (추정)
1. **스타 속도(Star Velocity):** 절대 수가 아닌 **상대적 성장률**이 핵심. 평소 2개/일인 레포가 하루에 50개를 받으면, 평소 100개/일인 레포가 150개를 받는 것보다 높은 trending 점수
2. **신규 레포 가산:** 생성된 지 7-30일 이내의 레포에 가산점 (새로운 것 선호)
3. **활동 지표:** 커밋, PR, 이슈 활동, 댓글 등도 부차적 요인으로 고려
4. **시간 가중치:** 최근 24시간 > 최근 1주일 > 최근 1개월 순으로 가중치
5. **언어별 Trending:** 전체 + 언어별 페이지 별도 운영 → 니치 언어에서 trending 진입이 더 쉬움

#### Trending 진입 전략
| 전략 | 설명 | 효과 |
|------|------|------|
| **런칭 집중화** | 하루에 HN + Reddit + X 동시 런칭으로 스타 유입 집중 | 높음 |
| **이미 활발한 날 피하기** | 대형 프로젝트 릴리스 날 피하기 (Apple WWDC, Google I/O 등) | 중간 |
| **니치 언어 공략** | Python/JS보다 Rust/Go/Zig 등에서 trending 진입 용이 | 중간 |
| **주말 런칭** | 평일 대비 경쟁 적음, 주간 trending에 반영 | 중간 |

#### Trending 진입 시 선순환
```
Trending 진입 → 일 500-3,000 스타 → 더 높은 Trending 순위 → 더 많은 노출
→ 뉴스레터/블로그 소개 → 추가 스타 → 1-3일 유지 후 감소 → 기존 대비 높은 베이스라인
```

### 6.3 스타 성장 패턴 분석

star-history.com 등의 도구로 관찰되는 3가지 주요 패턴:

#### 1. 바이럴 스파이크 패턴 📈
```
특징: 특정 이벤트로 하루에 수천 스타 급증 후 급락
원인: HN 1위, 유명인 트윗, 뉴스레터 소개
위험: 스파이크 후 관심 급감, "죽은 프로젝트" 인상
대응: 스파이크 직후 v0.2 릴리스로 모멘텀 유지
사례: GPT Engineer — 2개월 만에 40,000스타 (HN 바이럴), 이후 Lovable로 피벗
```

#### 2. 지속 성장 패턴 📊
```
특징: 일 10-50 스타가 꾸준히 유지, 완만한 우상향
원인: 실사용자 기반 확대, SEO, 문서화, 커뮤니티 성장
강점: 가장 건강한 패턴, 실제 활성 사용자 비율 높음
대응: 주간 콘텐츠 + 정기 릴리스로 유지
사례: Supabase — 초기 바이럴 후 지속적 성장으로 75K+ 스타
```

#### 3. 계단식 성장 패턴 🪜
```
특징: 정체 → 스파이크 → 정체 → 스파이크 반복
원인: 새 기능 릴리스, 컨퍼런스 발표, 미디어 노출 등 주기적 이벤트
강점: 각 계단이 새로운 사용자 층을 확보
대응: 분기별 "런칭 이벤트" 계획 수립
사례: n8n — AI 자동화 기능 추가 시마다 급성장, 계단식 패턴
```

- **AI 프로젝트 특화:** API 호출 기반 과금 (토큰 마크업, API 프록시)

### 7.3 번아웃 방지

오픈소스 메인테이너의 60%가 무급이며, 44%가 번아웃을 경험하고, 60%가 그만두었거나 고려 중이다(2025 설문 데이터).

#### 번아웃 신호
- 이슈/PR 응답 의욕 감소
- 프로젝트 관련 알림에 스트레스
- "의무감"으로만 유지보수
- 코딩 자체에 대한 흥미 감소
- 커뮤니티 부정적 댓글에 과도한 반응

#### 방지 전략

**1. 기대치 명시화**
```markdown
<!-- README 또는 SUPPORT.md에 추가 -->
## 응답 정책
이 프로젝트는 여가 시간에 유지보수됩니다.
- 이슈 응답: 영업일 기준 3-5일
- PR 리뷰: 1-2주
- 긴급 보안 이슈: 가능한 빨리
여러분의 이해에 감사드립니다. 🙏
```

**2. CODEOWNERS 활용**
```
# .github/CODEOWNERS
# 영역별 담당자 지정 → 리뷰 부하 분산
/src/core/        @maintainer1
/src/plugins/     @maintainer2
/docs/            @contributor1 @contributor2
/tests/           @contributor3
```

**3. 위임 전략**
| 업무 | 위임 가능 시점 | 위임 대상 |
|------|---------------|-----------|
| 이슈 트리아지 | 기여자 5명+ | 활발한 커뮤니티 멤버 |
| 문서 관리 | 초기부터 | 기술 작가, 사용자 |
| PR 리뷰 | 핵심 기여자 3명+ | 코드 품질 이해하는 기여자 |
| 릴리스 관리 | 핵심 기여자 1명+ | 신뢰할 수 있는 공동 메인테이너 |
| 커뮤니티 관리 | Discord 100명+ | 활발한 커뮤니티 모더레이터 |

**4. 경계 설정**
- 알림 시간 설정 (업무 시간 외 비활성화)
- "No"라고 말하는 연습 (모든 기능 요청을 수용할 필요 없음)
- 정기적 휴식 공지 ("8월은 여름 휴가로 응답이 느릴 수 있습니다")

### 9.2 MCP (Model Context Protocol) 생태계

#### MCP란?
Anthropic이 2024년 11월 오픈소스로 공개한 AI 모델-도구 연결 프로토콜. AI 에이전트가 외부 도구, 데이터, API에 표준화된 방식으로 접근하게 해준다.

#### 성장 지표 (2024.11 ~ 2026.03)
| 지표 | 수치 | 기간 |
|------|------|------|
| MCP 서버 다운로드 | 100K → 8M+ | 2024.11 → 2025.04 (5개월) |
| 월간 SDK 다운로드 | 97M+ | 2025.12 기준 |
| MCP 서버 수 | 5,800+ | 2025.12 기준 |
| MCP 클라이언트 수 | 300+ | 2025.12 기준 |
| 프로덕션 사용 서버 | 10,000+ | 2025.12 기준 |

#### 산업 채택
- **2025.05:** OpenAI, Google DeepMind, Microsoft, GitHub이 MCP 지원 발표
- **2025.05:** Microsoft Build에서 GitHub이 MCP 운영위원회 참여 발표
- **2025.11:** MCP 1주년 — Agentic AI Foundation(AAIF)으로 거버넌스 이관 (Linux Foundation 산하)
- **2026:** 벤더 중립 표준으로 확립, 에이전트 인터페이스의 "USB-C" 역할

#### MCP 생태계 오픈소스 기회
| 기회 영역 | 설명 | 기존 경쟁 |
|-----------|------|-----------|

### 타이밍의 중요성
- 트렌드 시작 후 **1-4주** 안에 프로젝트가 나와야 한다
- 너무 빠르면: 수요가 형성되지 않음
- 너무 늦으면: 이미 10개의 경쟁 프로젝트가 존재
- 최적 타이밍: "사람들이 이걸 필요하다고 느끼기 시작한 직후"
- **80% 완성도로 빠르게 출시 > 100% 완성도로 늦게 출시**

## 12. 적용 체크리스트

### 오픈소스 프로젝트 아이디어 추천 시 필수 점검 항목

#### A. 프로젝트 정의
- [ ] **한 줄 설명 완성:** "[동작] + [대상] + [결과]" 형태로 10단어 이내
- [ ] **Why Now 설명:** 왜 지금 이 프로젝트가 필요한지 트렌드 근거 제시
- [ ] **타겟 사용자 정의:** "모든 개발자"가 아닌 구체적 페르소나
- [ ] **JTBD 정의:** 타겟 사용자가 이 프로젝트를 "고용"하는 구체적 Job
- [ ] **10x 축 식별:** 기존 대안 대비 10배 나은 점이 무엇인지
- [ ] **기존 대안 분석:** 최소 3개 대안과의 차별점 명시

#### B. 아키텍처/DX
- [ ] 설치 → 첫 성공까지 5분 이내 가능한 구조
- [ ] 원클릭 데모(Codespaces, Docker, StackBlitz) 제공 가능 여부
- [ ] 플러그인/확장 아키텍처 고려 여부
- [ ] API 일관성과 에러 메시지 품질

#### C. README 설계
- [ ] Hook 문장이 3초 내 이해 가능
- [ ] Problem 섹션이 구체적 고통점 3-5개 나열
- [ ] Solution이 Problem과 1:1 대응
- [ ] 데모 GIF/스크린샷 계획 (15초 이내, 5MB 이하)
- [ ] 1줄 설치 명령어가 가능한 구조
- [ ] 배지 5-7개 계획 (CI, 버전, 라이선스, 다운로드)

#### D. 네이밍/브랜딩
- [ ] 이름이 2-3음절로 발음 가능
- [ ] npm/pypi/도메인 가용성 확인
- [ ] 이름에서 기능 암시 또는 강한 브랜딩
- [ ] 태그라인(10단어 이내 설명) 준비
